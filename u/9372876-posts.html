What Raigan's description does is project the centre of the circle onto the axis defined by the line.

To conceptualise what's happening, draw a line on a sheet of paper, and label the start point PS and the end point PF. Draw the circle with a centre at C. Now, look at the line so that it is perfectly horizontal from your perspective, with PS on the left. V is the line from C to PS, while D is the direction in which the line points.
Draw 3 examples at least, one where the circle is off the the left, one where it is above the line and one where it is off to the right. Draw in V for each one. Now here's the cool bit: extend the line PF-PS with dots every so often. Then draw a line so that it is perpendicular to PF-PS and also goes through the centre of the circle. The point where the line you just drew touches the extension of PF-PS is given by V.D (V.D is relative to PS).

Thus, if V.D is negative, the circle is to the left of the line. If V.D is larger than the length of the line it is to the right of it. Otherwise it must be in between.

I'll try to explain it:
You have a circle with centre C and radius r (note that C is a Vector2 and so has .x and .y properties, while r is a scalar).
You also have a line with start point PS and end point PF (they are also Vector2's).
D is the direction of PS to PF. It is essentially a normalised Vector2 of PF - PS.
V is a Vector2, the difference of C and PS.
V.D is the dotproduct of V and D.
If V.D is negative, the circle C,r is 'behind' the line and the closest point to C is PS.
If V.D is larger than the length of the line, the circle C,r is 'beyond' the line and the closest point to C is PF.
Otherwise the closest point is somewhere on the line (at PS + V.D(PF - PS)).

So (remembering that all the variables except r are Vector2's and not numbers):
D = normalise(PF - PS);
V = C - PS;
if(V.D < 0){
//Circle-circle test for collision between C,r and PS
} else if(V.D > length(PF - PS)){
//Circle-circle test for collision between C,r and PF
} else {
//Circle-line test for collision between C,r and (PS + V.D(PF - PS))
};

If we weren't using Vector2's this would be:
var Dx = (PFx - PSx)/Math.√(PFx*PFx + PFy*PFy);
var Dy = (PFy - PSy)/Math.√(PFx*PFx + PFy*PFy);
var Vx = Cx - PSx;
var Vy = Cy - PSy;
var VtimesD = Vx*Dx + Vy*Dy;
if(VtimesD < 0){
//Circle-circle test for collision between C,r and (PSx,PSy)
} else if(VtimesD > Math.√(PFx*PFx + PFy*PFy));
//Circle-circle test for collision between C,r and (PFx,PFy)
} else {
//Circle-line test for collision between C,r and (PSx + VtimesD(PFx - PSx),PSy + VtimesD(PFy - PSy))
};

Trying to convert vector math to non-vector math is harder than I thought it would be. Really, you should always use vectors (once you think in vectors everything becomes clear - or at least clearer), so try to master them before you do much else. One nice thing about vectors is that they have the same math in 2 dimensions and 3 dimensions. E.g. P - X is the line PX whether you're working with 2 dimensions or 3 (or more).

Why is your little flash game slowing down, you ask?

It seems that you forgot to clear() what was being drawn. So every 50 milliseconds, a filled circle was drawn. Since it's position was static you didn't notice. Basically, every time you drew on top of the circle it took more computing power. I think flash has to compute transparency effects even for opaque objects or something, but in any case, it slowed it down massively. So you just add to the first line of the render() function: sphoid.clear();

And there you have it: problem solved.

Find the two parallel lines that are tangential to the two circles, and extend them such that connecting the end points of either line results in another tangential interval.

It's like mattk210 said, I created two classes, Ray and Cone. The Ray class contains the instructions for each ray's actions, for example stepping it forward, checking for collision, rinse and repeat, as well as outcome of collision with various objects. The cone class simply creates a number of rays with equal angles between it and (using flash's drawing api) connects the dots and fills to make a cone shape.

All you need to do the raycasting is a point versus object collision detection system. Then you create code to the effect of:
1. Move point forwards along its direction vector
2. Does the point end up inside a blocking object?
a. If so, return which object it is, the final position of the ray and tell the global event handler what to do
b. If not, repeat steps 1 and 2 until you reach your destination

The tutorial I linked in the first post gives working code for such a system, but uses hitTest().

Imagine you have a group of objects. You know their names (for argument's sake, Apple, Banana and Pear). If you wanted to do something to all of them one after the other, you could hard-code it. Something like doStuff(Apple); doStuff(Banana); doStuff(Pear); etc. But what if you have a fourth thing? An array is a way of organising similar objects so you can do operations on them one at a time.

So on the main timeline, put the code
shotArray = new Array();

Then, when you create a new shota instance (line 4 of the cursor_mc code), put the instance into the array by using
this.index = shotArray.push(_root.shota.duplicateMovieClip( "shota"+shotacount, shotacount+7000)) - 1;
We use the same code to add the movie clip, but we put it into the array using shotArray.push(), and store the index of the point in the movie clip's value this.index (which is a variable we made up).

You also have to add some code to your main timeline code:
remove = function(bul){
    bul.removeMovieClip();
    shotArray.splice(bul.index,1);
};
and then change all the lines in the bullet code that say "this.removeMovieClip()" to "remove(this)".

Lastly, we need to make it so that your detection works on the bullets in their array. Change the code on enemya to:
onClipEvent (enterFrame) {
for(var i = 0;i < shotArray.length;i++){
    if (shotArray[i].hitTest(this)) {
        _root.score += 1;
        _root.enemyahp -= 1;
        remove(shotArray[i]);
    }
}

I think that should work, but note that it will get slow extremely quickly with lots of bullets and enemies! It has to do [#bullets] hitTests per enemy, so a total of [#bullets]x[#enemies] hitTests per frame. But really, it's as fast as such a system can be before optimising while still using hitTest becomes farcical.

px = point.x - circle.x
py = point.y - circle.y

if absolute(px) == r and absolute(py) == r:
	T1 = (px,0)
	T2 = (0,py)

else if absolute(px) == r:
	T1 = (px,0)
	L2 = px*px + py*py
	px2 = px*px
	T2 = (-px2*px/L2,px2*py/L2)

else if absolute(py) == r:
	T1 = (0,py)
	L2 = px*px + py*py
	py2 = py*py
	T2 = (py2*px/L2,-py2*py/L2)

else:
	px2 = px*px
	py2 = py*py
	r2 = r*r
	D = sqrt(px2*py2 - py2 + r2)
	mb = px2 - r2
	pxpyonmb = px*py/mb
	Donmb = D/mb
	m1 = pxpyonmb + Donmb
	m2 = pxpyonmb - Donmb
	temp1 = r/sqrt(1 + m1*m1)
	temp2 = r/sqrt(1 + m2*m2)
	T1 = (m1*temp1,-temp1)
	T2 = (-m2*temp2,temp2)

T1.x += circle.ox
T1.y += circle.oy
T2.x += circle.ox
T2.x += circle.oy
Note that this is pseudocode. Note also that I haven't tested this beyond deriving the maths for it, and the maths has one major downside: minus signs become ambiguous. In other words, you may have to add test cases to find out whether they work (preferably with a graphical display) and fiddle around with special cases and changing signs accordingly.

Cases you should check to see if you need to change signs for:
px*py > 0
px*py == 0
px*py < 0
mb > 0
mb < 0

I redid the maths and came up with a vastly more elegant and computationally-simple solution.

px = point.x - circle.x
py = point.y - circle.y

if px == 0 and py == 0:
//No solution is possible. Alternatively, any point on the circle is a solution. Take your pick.
return null

r2 = r*r
px2py2 = px*px + py*py
D = r*sqrt(px2py2 - r2)
pxr2 = px*r2
pyr2 = py*r2
T1 = (pxr2,pyr2)
T2 = (pxr2,pyr2)
pxD = px*D
pyD = py*D
T1.x += pyD //may need to edit
T1.y -= pxD //these lines to
T2.x -= pyD //get correct signs
T2.y += pxD //for the right result
T1.x /= px2py2
T1.y /= px2py2
T2.x /= px2py2
T2.y /= px2py2

T1.x += circle.x
T1.y += circle.y
T2.x += circle.x
T2.y += circle.y

As you can see, this version is much faster (only 1 square root), and only has one special case (where px2py2 would be 0). There might still be the ambiguity, but I don't think so. Also note that this is the absolute minimum of computation possible. You simply cannot get a more efficient method than this (unless you are a programming deity of some sort).
