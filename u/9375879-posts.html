#416420 9 2008-03-13T02:54:11Z taaveti
Ah, so you're only checking the closest (in some heuristic measure) tile for collisions? I thought your problem was that you were finding a collision with the first tile, moving the object away, and then not finding the collision with the second tile because the object isn't there anymore. If you were testing against all tiles in some neighborhood around your object, then delaying the movement until after all the testing would make sense, but it doesn't change anything if you're only testing against one tile.

My thoughts on merging tiles into shapes, which may or may not be relevant: you don't necessarily have to know all the tiles in a given shape, just which tiles are next to the current one along the relevant surface. This could be accomplished by adding a "neighbor" pointer to each vertex, which would essentially mean "this other object also has this vertex." Then, if your contact line segment includes that vertex, you also test the neighbor (and, if necessary, extend the contact segment). Just remember to do something to prevent mutual recursion (e.g. Tile A says "this vertex is also part of Tile B," so you check Tile B; Tile B says "this vertex is also part of Tile A", so you check Tile A...).
#418195 85 2008-03-18T02:52:23Z taaveti
Really, though, we shouldn't have to worry that much about gravity. For the simplest case, a teleporter only really does anything for two frames, which means we only change the distance travelled for one frame (and that change is only going to be one frame's worth of gravity, which should be pretty small). This shouldn't get to be a big issue until you start dealing with complicated multi-holed teleporters (i.e. those which take more than two frames). But one could guess some (small) number for gravity, which would be close enough for one- and possibly two-holed teleporters, and then update that number later when the source is released.
