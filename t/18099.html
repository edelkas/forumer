#336944 2 2007-06-29T15:44:51Z Raigan
We spent quite a while attempting to do something similar (i.e given several individual penetration vectors, "combine" them somehow to generate a single correct penetration vector), and in the end we never found anything that worked better than just pushing the object out of each collision individually.

It might help you to think about the real/correct result you're trying to approximate: your tests are equivalent to shrinking the box down to a point, and inflating the tiles by the box's dimensions, then finding the point in the inflated tile surface closest to your box-point. The boxpoint->closestpoint vector is the correct penetration vector.

This sort of inflation-by-a-shape is called a Minkowski sum, and I find it incredibly fascinating, it's just really, really weird and interesting. It's quite a strange idea to wrap your head around; here's a site that might help, it shows two shapes and their minkowski sum: http://www.cut-the-knot.org/Curriculum/Geo...yAddition.shtml

This site has some great tutorials:
http://essentialmath.com/tutorial.htm

This one specifically should be a good read: http://www.eiserloh.net/gdc2006_Eiserloh_S...icsTutorial.ppt

#338430 7 2007-07-03T17:37:25Z Derakon
What I ended up doing for multiple-tile collisions was to store all collisions that occur in a given frame, and then after they've all been collected, iterate through them to find the right reaction. That is to say:

* Object A collides with terrain object B, generating backout vector u, which is stored
* Object A collides with terrain object C, generating backout vector v, which is stored
* Object A looks at u. Will backing out along u prevent collision with both B and C? If so, then use u as a backout vector. If not...
** Object A looks at v. Will backing out along v prevent collision with both B and C? If so, then use v as a backout vector. If not...
*** Object A applies both u and v to back out (or, in a case of colliding with three or more objects, it keeps applying backout vectors until it is no longer colliding with anything).

Note that this does not handle case C, which I've resolved will simply not occur in my game.

Also, I have a hack in place specifically for when the player's X velocity is neglible, their Y velocity is aligned with gravity, and they hit something with a normal opposed to gravity. In that particular case, they're probably "standing" on some terrain, so instead of backing out along the surface normal of the terrain, I back out along the object's velocity vector. This keeps objects from slowly sliding down slanted terrain.

#441477 13 2008-06-03T04:42:25Z mattk210
it definitely won't be infinite (as many times as there are overlapping tiles), and storing simple values without even doing much calculation is nothing for modern computers

as for the actual problem, i semi-solved it in my game using a partial implementation of a system raigan described with inflated edges:

Quote
hi,
This is a fundamental problem with any sort of tile-based collision, which is: you're only solving the problem on a tile-by-tile basis, not for all tiles at once. the reason is that solving for all tiles at once is _much_ harder.

To answer your follow-up question, there is no simple way to add (or otherwise "munge") individual penetration info from different tiles to get a single vector that solves them all together. We spent quite a while about a year ago trying to figure out if this was possible, and concluded that it just isn't -- you have to solve the all-at-once problem for real if you want a good solution.

One approach that might be very useful is to look at the problem from a different point of view: instead of circle-vs-world, think of this as point-vs-inflated-world: shrink your circle from radius = r to radius = 0 (i.e a point), and expand/inflate the world by r. This is an equivalent problem (i.e a vector that moves the point to the surface of the inflated world will also move the circle to the surface of the non-inflated world), but it's a bit easier to see what you're actually trying to do.

I'll attach a picture of what i mean -- in the picture, the actual surface of the world is grey, and the inflated surface is black.

If you sketch out these sort of things you'll find a pattern:
1) if your circle is penetrating only one edge of the world (a line or a circular arc), it should be pushed out of that edge along the edge's normal, by the amount of penetration (i.e this is what the tutorial code does)
2) if your circle is penetrating _two_ edges, then it should be pushed out to the point where the two edge's  _inflated_ versions intersect.

the problem with (2) is that it's still only a local solution, i.e it will fail in cases where the circle penetrates more than 2 edges at once (in such cases there really 0 solutions, because the 3 or more inflated edges may not all intersect in a single point), or where the two edges' inflated surfaces never intersect (i.e if they're parallel).

We spent some time trying to explicitly generate the inflated-intersection points, etc, but in the end it was much faster to calculate the inflated surface approximately, by using the "repeatedly push the circle out of a single edge" method.

raigan

although this method may require a lot of changes to work for AABB's as well as circles
