#413814 2 2008-03-04T16:33:26Z Raigan
well, this is where it gets complicated

for one thing, there won't always just be the one contact point -- if an edge of the box is parallel to an edge of the tile, there will be two contact points (or, more correctly, a contact lineseg.. but this is approximated as two points, on on each end of the seg).

your idea of intersection can be simplified a bit using information you know from the axis tests; if you keep track of the edge+object that "generates" each axis, then at the end (when you have a single axis and penetration amount) you'll also have an edge on one of the objects -- you know that the contact point lies somewhere on this edge.

you then need to find the feature on the other shape which is "furthest" along the -ve axis.. this is hard to explain, basically if the penetration axis is from the box (and points outward from one of the box's edges) then you want to find the point (or edge) on the tile which is furthest "towards" the box.

this "furthest in a direction" idea is usually called "support mapping".. if it's a point, you can find the point on the other object's edge closest to it, and then you have the contact point on both shapes. if it's an edge, you need to clip the two edges together.. it's messy.

to be honest we've never bothered to implement this -- for one thing, if you don't need real boxes but just want some box-like objects, two circular particles connected by a stick can be very convincing


also, this can get a bit tricky with circular shapes!

mostly, once you move from particles to full rigid bodies, SAT in 2D becomes less simple and attractive. for special cases like box-box it can still be great (see box2d for some source), but to handle a broader range of cases without lots of complicated code, you might be better off looking at other algorithms such as GJK or XenoCollide.

#415961 5 2008-03-11T21:16:25Z Raigan
this is one of the problems with tiles -- they don't explicitly describe the shape of the world, so you end up with edges where there should just be a single smooth surface.

i don't know if there's a perfect solution, you could try adding some checks, but too much work in that direction and you're better off just merging tiles together (so, just one edge instead of two in your case), which can be tricky to get working..

#416420 9 2008-03-13T02:54:11Z taaveti
Ah, so you're only checking the closest (in some heuristic measure) tile for collisions? I thought your problem was that you were finding a collision with the first tile, moving the object away, and then not finding the collision with the second tile because the object isn't there anymore. If you were testing against all tiles in some neighborhood around your object, then delaying the movement until after all the testing would make sense, but it doesn't change anything if you're only testing against one tile.

My thoughts on merging tiles into shapes, which may or may not be relevant: you don't necessarily have to know all the tiles in a given shape, just which tiles are next to the current one along the relevant surface. This could be accomplished by adding a "neighbor" pointer to each vertex, which would essentially mean "this other object also has this vertex." Then, if your contact line segment includes that vertex, you also test the neighbor (and, if necessary, extend the contact segment). Just remember to do something to prevent mutual recursion (e.g. Tile A says "this vertex is also part of Tile B," so you check Tile B; Tile B says "this vertex is also part of Tile A", so you check Tile A...).
