#65758 13 2005-05-14T15:50:33Z Raigan (guest)
hi,
looks good!

if you read through our tutorial A, and/or the flashinthecan presentaion, you'll see that in order to get bounce/friction working, you need to know (for a given collision) the unit vector which describes the collision direction.

then, you use the unit vector to decompose the particle's velocity into two vectors: one parallel to the collision direction (this is used for bounce), and one perpendicular (this is used for friction).

about the velocity-less thing, it is weird but you'll get used to it. anyway, if you need to know the velocity of a particle, it's just (v = newpos - oldpos). likewise, if you want set the velocity of a particle to v, just move the oldpos (oldpos = newpos - v) or the newpos (newpos = oldpos + v).

raigan

#65845 15 2005-05-14T19:10:02Z Raigan (guest)
i'm 100% positive i know your problem: you're using _x and _y, which (for some reason) are implemented as single-precision floats.. any user-defined numbers are double-precision floats.

try assigning each movie clip a .x and .y, and use THAT as the basis for all calculations; at the end, just set mc._x = mc.x, mc._y = mc.y to align the graphics with the particle position.. that should fix the drift. at least, we had that exact problem a long time ago, and that's how we fixed it.

of course, increasing the precision isn't a _real_ solution; the actual problem is that the math we're using isn't numerically stable, and we should rearrange it so that it doesn't suffer from floating-point problems. but we haven't tried that yet as we're lazy

raigan
