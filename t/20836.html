This picks up from another thread...

So, I've been working on a general Flash/AS3 game (dynamics) engine for a while. I originally used a ported version of the N tutorials found on this site for collision detection. As great and *fast* (and they are fast) as they are there are a number of issues:

1) Each tile has a complex custom implementation (this give it the speed).
2) Creating new tile type is complex.
3) There is lots of code.
4) Its not possible to introduce continuous collision detection using this code base (as far as I'm aware)
5) There really is lots of code...

I started to play around with different tile description systems and realize a few things:
1) on a 3x3 grid (plus a center point) - there are actually lots (>100 I think) of convex tiles.
2) of all these tiles, there are only ever 8 separating axes (horizontal,vertical,45 left and right, 23 left and right and 67 left and right)

The engine I'm building only allows bodies to be built out of rectangles (2 axes with angualr velocity) and circles (3 axes). This allowed me to write something that actually pre-calculates all intervals for the tiles and bodies at startup. The at run time, the engine is feed the body position, orientation and speed - the collision detection is then just a few look ups in an array. There is no object create/deletion going on.

The tile definition system is based on a bitmask. If a tile grid is defined as:

001--128--064
.|........|........|
.|........|........|
002--256--032
.|........|........|
.|........|........|
004--008--016

Then a full, square tile has the ID 85 (1+4+16+64 or 1010101).
A 45 degree half tile, slope normal 1,-1 has the ID 21 (1+4+16).

My tile reference array is built as simply as:

tileArray.push( new Tile(hw, 85));
tileArray.push( new Tile(hw, 21));
tileArray.push( new Tile(hw, 69));

and there are less than 200 lines of code for the tile.

The axes are calculated as the tile mask is parsed, so no need for a separate axes mask.

There is a very early demo here of some of the most interesting tiles:

http://home.planet.nl/~borst595/CachedSAT.swf

Mouse + left click to move rectangle. Scroll wheel to rotate the rectangle.

I'll release the source as soon as possiable. If anybody is interested before that then PM me here and I'll email it you.

#393812 4 2007-12-27T16:09:39Z rje
Quote: mattk210, 2007-12-27T02:21:51Z
Also, something like this would be fast, right? comparable to N's engine?

Yes and No. The thing with N's tile collision detection is that:

a) it only supports AABB's and circles
b) the collision code doesn't need to loop through vertices. The average case only ever seems to need 10 or so actual lines of code to calculate collisions.

The code for this example looks like a 'normal' SAT implementation except for the precalcualted part but it still needs to (worse case) loop over 9 verticies for each collision test. The real speed up should be the swept collision tests. In my old engine I had very small objects moving fast, I used to multisample the objects which lead to up to 10 tests per frame.

As for curved tiles, I'm not sure what to do about them at the moment. I'd dont think I need them, but if they are not to difficult to implement I'll have a go.

#403701 15 2008-01-24T08:52:53Z rje
Sorry for the late reply.

It does support OOB. Once the OOB is calculate ONCE pre rotation it is cached and used on all collisions for that frame. For example we might be checking on a 9x9 grid around the OOB. The intervals are only calculate once for each project, cached and reused from that frame (beacuse there are only ever 8 tile axes).

There is no ray casting at the moment - hopefully have that some point soon - its very important.

I'll post the source in this thread.

The multiple collisions can be a problem sometimes. Mainly on flat, vertical surfaces. I tried a number of things, I think the most success full is just to just the adjacent tiles, and if its also flat the only project in one direction. I know its very limited.

I've been working on some Rigid Body stuff - I used the C Chipmunk library as a basis and used the interesting parts (SI solver etc) in my own engine. This doesn't have tiles support or raycasting. In fact it has nothing apart from an extremely fast rigid body engine, but its a good start.

Demo: http://home.planet.nl/~borst595/pEngine.html

And for the problem of multiple tiles, try this:

Calculate and store the average length of every object touching the object that needs to be constrained by walls. Then sort that list by average, highest average at top. This will solve the problems illistrated by A and B in the Weighted System thread. If you also have multi sampling, your character won't fall too far down the tile to be moved to the right or left if inbetween two tiles (assuming you let gravity constantly pull your character down though the floor)
