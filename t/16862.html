I thought of putting that into Serious Discussion because of the seriousness involved, but then I realized it's much too serious and important to make a joke out of it.

What many of you, mainly highscorers, and that actually included me, have been waiting for is N1.5 which, as it was said, is supposed to have several anti-cheating functions, like that Cheat Engine protection that Unreality made.

Seeing as the release of Robotology and N1.5 is drawing closer, we should actually think about how to solve some problems involved, though.

This thread is meant as a serious discussion for all people who are interested and claim to have some programming skills. It's about brainstorming solutions to problems that I see and that other people may see.

And with this I start:

Demos and times can be submitted to the server directly, meaning that no instance of N is running. That's what you see on 0-0 for example. There are two solutions to that problem:
1. A bot that is checking every demo on the highscore board, seeing if it gets to the exit or not, and if yes, at what time.
2. Some sort of Server-Client recognition I have no idea about. That would imply that the demo must be submitted with N, using some sort of signature. The implementation of that feature into Flash and the possible ways to by-pass it have to be regarded! What if someone is still able to hack the .sol or the file where everything is saved?

Which leads us to the next problem, which I see as the most important and most unsolvable problem of all:
What if someone just fbf's/uses a manipulated version of N to get a demo and submits it?
We're pretty helpless against fbf. The only way I thought would be possible is an encryption system. Playing the normal game, every demo would be encrypted in some way. Actually, not just some way: It has to be a goddamn excellent way. If you're playing in fbf, the demo would be encrypted differently or not at all, so it's possible to distinguish fbfed from normal demos.
The flaws of this are obvious: There's always a way if you just try hard enough. Cheaters will probably find a way through this...

Well, there are several was that this could be approached (at least in my mind).
First, we need to consider in what language N 1.5 will be coded in
...Oh wait, just had a brain fart and remembered that since its going to be an update, its going to be in Flash...
Anyways, security in flash is and probably will continue to be a problem for a long time. If we're concerned about people hacking the .sol file, then M&R can encrypt the data that is stored in the .sol file. Anyone willing to spend their time trying to hack the .sol file will end up seeing what they consider to be gibberish.
Unfortunately, this will lead the hacker to look for the key in the .swf file, where the key is built in. This will lead people to want to decompile N 1.5. Even if it's stored in an .exe file, it is still de-compilable. This is, unfortunately, where-in on of Flash's main weaknesses lies.
So now, we have to pretty much abandon the local security idea, because Flash hardly gives any good options in security on the local scale, but then again I guess Flash is mostly used for the internet...
So probably, our only true hope for security is between server-client communications. And since we already know that the client side is in no particular way secure, we must rely in the server side for our security.
The way i see it, I think the information that would have to be sent to the server would have to contain everything that it contains right now, along with . Of course, all of it would have to be encrypted. I agree that we'd need some sort of bot or algorithm for detecting hijacked demos. After doing some thinking away from this post, I realized that probably the most secure way to send data through Flash would be to use some sort of encryption method involving two servers. The first one would be for requesting keys for a select algorithm implemented in Flash, and the second one would be for submitting the actual high scores. heck, those two servers could even be combined into one, and just have the different requests as parameters.
Personally, I think that if N was just coded in C++ security wouldn't be a major problem, although non-Windows users would miss out. I hope it doesn't come to that.

And as my last suggestion/realization, we could use .sol files. The method I'm thinking of would involve saving the key inside of the .sol file. Parts of the key could be saves along with the encrypted data.

Well, at this point, I think my brain is about to give out...
