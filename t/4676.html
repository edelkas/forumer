A soduku solver is an interesting problem in itself and can give a more general overview toward problem solving. I haven't looked at your code so I appologise if I am rehashing something you already know.

If you want to do it properly the most thorough way is to use formalise it as a Constraint Satisfaction Problem (CSP). This is quite a headache unless you plan on writing it in Prolog and in this case may be over kill. Here is a link I quickly dug up on Google: CSP Examples.

You could phrase the problem as a simple search problem using a recursive depth first search (DFS). This basically means looking at every possibility from a particular partial solution. This would likely take forever unless you prune the search space by removing impossible results. Phrase each square as a set of 9 possibles and then score out all those which must be removed from each square as you go. For example if you have a 3 in a group you can remove 3 from all the sets in that group as well as those in the same row and columb. There is a lot of wangle room for getting free information in Soduku.

A silly way, which would be quite fun, would be to use a Genetic Algorithm (GA). GA's express solutions to a problem as a DNA like encoding. The idea is you generate a whole bunch of random potential solutions to the problem and then evaluate how well each solves the problem. Those which perform best are 'bred' with each other to provide the next generation of offspring. The hope is these offspring will include the strengths of multiple parents. Despite sounding awfuly complicated, GA's are actually rather simple to implement. The difficulty is in working out how to express your problem as a DNA like representation and how to evaluate how close a potential solution is to a real solution.
