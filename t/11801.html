#213565 4 2006-08-09T14:57:34Z Raigan
one thing specific to your game would be to try considering _two_ segments at once, instead of one-by-one.. so, you'll have to write code that projects a point out of a "V" shape. we actually did something like this as a test a couple years ago..


for convex Vs, just find the penetration with each side and push out of the smallest one (or, push out of whatever side the rest of the box is on, or whatever). if the point isn't penetrating one of the segs, it's not penetrating either.


for concave Vs, it's slightly trickier. first, test if the point is "behind" the lines that contain the linesegs (it's behind if the dotprod of the line normal and the point-on-line->test-point vector is -ve). if it's not behind either, no hit. if it's behind one but not the other, just project it out of that one. if it's behind both, things get slightly more complicated: you'll either have to push it out of one of the segs, OR push it to the point where the segs intersect.

if you understand about voronoi regions you can usee them to decide what to do in this case: if you're in the VR of the point where the segs meet, then project out to the point, otherwise you're in the VR of one of the segs -- project out of that seg.

hopefully this makes sense or at least gives you some ideas. mainly, i don't think you can't solve this problem if you only consider each segment in isolation. i really wish i knew better resources or more theory about this sort of thing, because it's something that happens all the time (i.e you have to add extra information in order to represent something you want).

you can even extend this idea to handle points with size (i.e circles).

I successfully solved the main problem (the points falling between segments), but in a sort of a hack-y manner. I tried to implement a line-based collision response system, but it slowed the processing down unbelievably (which most likely means I wasn't implementing it properly), so I converted the floor segments into a new class which would only project points out of the 'first' face (in this case upwards out of the floor). This also meant that I could get rid of the simple maximum and minimum constraints for colliding with the world (now I use 4 single-projection direction walls).

This method didn't solve the secondary problem of the box lines passing through the floor and other shapes, but for my purposes it doesn't matter. What I have now is a reasonably fast collision detection system, that looks fairly good (considering that it is just using the drawing API).

Now I have a question about implementing friction and bounce. If the projection vector of a point out of a line is (direction of right-hand normal of line)*(projection distance) and the perpendicular to this is (direction of line)*(projection distance), how do you calculate how far to offset the old position of the particle to factor in friction and bounce?
