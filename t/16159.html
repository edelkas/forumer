I'm developing a collision detection and response function for a physics based game based on Metanet's tutorials. So far, the function detects collisions perfectly, and *sometimes* responds correctly.

The problem I'm having is that I am able to find the projection magnitude, but the vector is sometimes the reverse of what it should be. Instead of the two shapes being moved apart, they are attracted, causing another collision to be detected with a greater magnitude. This repeats until the shaped separate, in the opposite direction intended, at high speeds. I believe the problem is that I'm only using the right hand normal as my projection vector, rather then deciding which to use.

My question is this: Is there a simple way to determine which projection vector to project on so that the shapes will always separate and never attract? If not, is there an easy way to detect whether they will attract, so that I can reverse the vector?

I'm attaching my swf. Note that collisions with the bottom triangle are functional. This would not be the case if the other two objects were to approach from the bottom.

#304430 3 2007-03-11T16:42:39Z Raigan
do you know the axis/line that contains the projection direction? that's what it sounds like: in this case, you just need to determine which direction to move along the line (i.e +ve or -ve).

you could look at the dotproduct of the A-to-B vector and the projection vector you're using, and negate the projection vector depending on if the sign of the dotproduct is +ve or -ve.
#308948 4 2007-03-30T23:05:20Z mtthwhys
Hello Nich,

I had a problem just like this really recently... in my case it turns out that I had inadvertently reversed the "voronoi region" indices... oH = 1 instead of -1... in the part of my code that was looking for collisions from a diagonal cell. As such, the object would appear to enter the tile's space inappropriately, and then suddenly pop to the edge/vertex.

There was some other thing too, but I can't remember now how I solved it, besides tracing out the collisions... in the N tutorials they've got it set up to trace something like:

trace("\tBAD collide() tile(" + t.pos.x + ", " + t.pos.y + ") ._type = " + t.type + " ._ctype = " + t.ctype);

Something LIKE that in the CollideCircleVsTile/CollideAABBVsTile objects. It helped a lot to follow that, although, I've gotten pretty far away from the tutorials by this point.
