#325199 2 2007-05-29T02:51:48Z Raigan
I think there may be a bug in your code -- it's true that using the tutorial method the projection direction may "jump" from one face to another, but it should never push the object down into the tile -- the object should be pushed _up_ by m.

The overlap/penetration on a given axis doesn't have a sign/direction, so for a given overlap there are two potential directions to project: +n or -n, where n is the axis vector. There are several ways to choose which direction to push, one being to project the objcenter->objcenter vector onto n and see which way that points.

Another option is to rearrange your axis tests so that the direction info isn't lost; the only reason you have an ambiguous +n/-n case is that you're calculating the unsigned overlap along the n axis -- instead you could calculate the _signed_ overlap along +n and -n seperately. This will result in more axis tests (i.e objects with parallel faces can't "share" axis tests) but may help simplify things for you.

Thanks very much! I should've thought to check the normal before returning; stupid mistake. I just added this to the end of my doSAT function:
    //Minor fix time - if the normal we have calculated would push the polygon
    //*towards* the other polygon, as can happen in certain cases with acute
    //angles, then flip the normal.
    if (result.normal.dot(alt->getCenter() - center) < 0)
    {
        result.normal = result.normal * -1;
    }
and now the bug is gone.

I could probably fix this more elegantly (i.e. when the normal is first calculated instead of when I'm returning results), but dot products and if statements are both cheap, so I'm not too worried. Correctness is paramount right now.

#327428 9 2007-06-04T20:25:26Z Derakon
Well, the solution I postulated in my previous post worked. In short:

1) update() is called on all objects/sprites, during which time they perform whatever physics modifications they need.

2) The engine checks all sprites for collisions with each other.

3) When a collision occurs, sprite A notes down all details of the collision (surface normal, backout distance along normal, backout distance along velocity, name of other object).

4) After all collision detection has been done, update2() is called on all objects. Sprite A calls its processCollisions() function, which:

4a) checks every collision that occurred, to see if any one backout attempt clears A of collision with all other collided objects. If so, it uses that backout; if not, then

4b) it performs the first backout, then gets collision data for the second object, performs that backout, and iterates until it has done backouts for all objects.

Fortunately, in most cases the player is unlikely to be colliding with more than two terrain tiles at a time; three if they're backed into a right-angle corner. Still, the addition of an entire second update cycle, not to mention all the extra collision checks, rankles. 4a requires performing N * (N - 1) collision checks, and 4b requires an additional N such checks. I'm just glad that SAT is good at short-circuiting when possible.

Mind you, at the moment my costliest code is the part that blanks the screen each frame. I'll eventually remove that (since I'll be drawing every pixel every frame anyway, blanking won't be needed), but drawing will remain expensive compared to everything else.
